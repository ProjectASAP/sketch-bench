# `aqpbm-planeval` design

The crate `aqpbm-planeval` is trying to answer one question:
how much advantage can I gain by introducing approximation to my query.

This is the planned phase 2 of aqpbm.
At this stage, the query IR before and after are generated by `ASAPPlanner`.

This design doc of `aqpbm-planeval` contains the following contents:

- input: `pre-asap-dag`
- input: `post-asap-dag`
- output metrics
- evaluator design
- how to read the output

## Input

There are two input designed to be connected at this moment.
One is `pre-asap-dag` that represents how a query looks like "originally" or "without approximation".
The other is `post-asap-dag` that represents what the query looks like if part of the query is replaced by approximation.

### `pre-asap-dag`

This is a enum that imported from `pre-asap-dag`.
This enum is indicating how the query operates: the scan, aggregate and query.
Thus, the enum is processed one node by one node.

### `post-asag-dag`

It is chosen to use the flatten node list from `ASAPPlanner` to fully utilize approximation.
Each node is still processed one by one.

### Data

Data is generated by `aqpbm-datagen`.
User has the flexibility to choose what the data shape looks like.
Currently, user are expected to be "kind", which means there are no correctness checking for incompatible data shape and query.

## Output

Output is a set of metrics chosen by user.
Query represents a complete scan-aggregate-query lifecycle.
Scan of data is ignored here.
Data are generated in-memory to represented the scan of data is complete.
Thus, the output will be fixed to be the following number:

- aggregate time
- query time
- total memory usage
- accuracy

## Evaluator Design

### Pre-ASAP evaluator

The `pre-asap-dag` is a tree like structure.
Thus, the evaluator will evaluate the tree recursively.
The time of each node of the tree is computed by timing functionaliy in `aqpbm-core`.

### Post-ASAP evaluator

The `post-asap-dag` is a list.
Thus, the nodes are processed one by one.
