This conversation has identified the critical "Fairness Gaps" in current benchmarking practices (like those found in the AWS or Google Benchmark models) when applied to ultra-fast data structures like sketches across C++, Rust, and Go.

To refactor your benchmark to reach "Gold Standard" fairness while remaining extensible, follow this finalized design goal and requirement list.

🎯 High-Level Design Goal
"Binary-Isolated Monolithic Execution": Every sketch variation must be compiled into a standalone, specialized binary to eliminate instruction alignment shifts and branch predictor pollution, then executed under strict environmental controls (CPU pinning and frequency locking) by an external orchestrator.

📋 Refactoring Requirements (LLM-Friendly List)
1. The "Case 1" Architecture (Process Isolation)
One Binary Per Sketch: Refactor the build system (CMake/Cargo/Go Build) to produce a unique executable for every sketch variation. Never run two different sketch types in the same process lifetime.

Shared-Nothing Logic: Each binary must contain only the code necessary for its specific test to keep the instruction cache (L1i) clean.

2. Zero-Cost Extension Pattern (The Adapter)
Static Dispatch Only: Use C++ Templates or Rust Generics (Monomorphization) to wrap user-provided functions. Avoid virtual keywords, dyn traits, or any interface that uses vtables.

Glue Code Injection: Design the system so users only provide the "Insertion Snippet." The orchestrator should inject this into a Standardized Timing Template before compilation to ensure the loop logic is identical for everyone.

3. Environmental Control (The Orchestrator)
CPU Pinning: Use taskset or numactl to pin every benchmark run to the same physical core to ensure identical cache and thermal conditions.

Frequency Locking: Before execution, the orchestrator must disable "Turbo Boost" and set the CPU scaling governor to performance.

Process-per-Trial: Run each implementation as a fresh process. If performing 10 trials, launch the binary 10 separate times rather than looping 10 times inside one binary.

4. Data & Timing Protocol
Pre-Allocated Buffer: The binary must load the entire 1M int64 dataset from the binary file into RAM before the timer starts.

Internal High-Res Timing: Use nanosecond-resolution monotonic clocks inside the language (e.g., Instant::now() in Rust, std::chrono in C++) to measure only the insertion loop.

Mandatory Warmup: Every binary must perform a "Warmup Phase" (e.g., 100k insertions) to prime the CPU pipelines before the 1M-insertion measurement phase begins.

Compiler Fencing: Use "Black Box" hints (e.g., std::hint::black_box) to prevent the optimizer from deleting the insertion loop if the results aren't explicitly used.

5. Output Standardization
Uniform Reporting: Every binary must output a standardized format (CSV or JSON) to stdout containing exactly two fields: implementation_name and total_nanoseconds.

External Aggregation: The orchestrator collects these individual outputs to generate the final comparison visualization.
